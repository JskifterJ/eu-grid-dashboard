# ADR 0001: SQLite for historical data storage

**Status:** Accepted · 2026-04-20
**Deciders:** Johannes Skifter

---

## Context

The dashboard needs to persist historical ENTSO-E grid data (daily summaries of CO₂ intensity, day-ahead price, and renewable share per country) so that:

- The historical context strip can animate the choropleth map backward across months or years.
- The naive seasonal baseline (same-hour-same-weekday mean, last 4 weeks) has local data to draw from rather than making ENTSO-E API calls on every request.
- Forecast evaluation (7-day MAPE) can be computed without live API round-trips.

The data has specific characteristics:

- **Small volume.** ~35 countries × 8760 hours/year × a few metrics = ~1 M rows/year. Easily fits on disk.
- **Write-once, read-many.** Historicals are immutable once written. The only write path is a scheduled backfill cron job, never concurrent user requests.
- **No relational joins across schemas.** Queries are simple time-range scans per country-metric pair.
- **Deployed on Render.** Render's free and starter tiers do not include a managed Postgres addon; adding one costs money and operational overhead.

---

## Decision

Use **SQLite on disk**, accessed via Python's standard-library `sqlite3` module (wrapped in `app/historical.py`).

The database file lives at a path configured via an environment variable, defaulting to `data/historicals.db`. In development it lives in the repo working directory; on Render it lives on the instance's ephemeral disk (acceptable because the backfill cron regenerates it from ENTSO-E if the instance restarts).

Reads from the historical endpoint are cached in-memory for 24 hours via the existing `Cache` class, so the SQLite file is touched at most once per country per day in normal operation.

---

## Consequences

**Positive:**
- Zero ops overhead. No connection strings, no managed service, no addon cost.
- The DB file is trivially committable (or `.gitignore`-able) in development.
- Standard-library access means no additional dependency.
- Concurrent-write limitations are irrelevant: only the backfill job writes, never user requests.

**Negative / tradeoffs:**
- Single-file database: if the Render instance restarts and the disk is ephemeral, historicals must be regenerated by the cron. This is acceptable — the dashboard degrades gracefully to the seasonal-baseline fallback during regeneration.
- Not suitable if the architecture ever requires multi-region writes, high write concurrency, or a shared database across multiple Render instances. Replace with Postgres at that point.

---

## Alternatives considered

| Option | Why rejected |
|---|---|
| **Postgres (Render addon)** | Adds ~$7/month, connection-pool overhead, and a managed-service dependency for a workload that needs none of these capabilities. |
| **Flat Parquet files** | Harder to query ad-hoc (requires pandas or DuckDB in the request path); no indexing. Acceptable for batch analytics, not for per-request latency. |
| **In-memory only** | Data lost on restart; seasonal baseline and eval panel become unavailable until the cron runs again. Unacceptable user experience. |
| **DuckDB** | More capable than SQLite for analytical queries, but adds a non-stdlib dependency with no material benefit for this query pattern. Reconsider if query complexity grows. |
